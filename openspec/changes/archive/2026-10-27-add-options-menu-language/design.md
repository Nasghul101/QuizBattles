## Context

Existing pieces: `Utils.set_app_locale()` applies and persists `locale` in `LocalCache`; `Utils._bootstrap_locale()` resolves stored -> OS -> `en`; `SUPPORTED_LOCALES = ["en","de"]`. The scene already has `OptionsButton`, `OptionsPopUp` (script `pop_up.gd`), `LanguageOptions` (OptionButton: English/Deutsch/繁體中文, ids 0-2) and `RevertChangesButton`; the latter two have no connected signals. `TriviaQuestionService._get_user_language()` reads a `language` key that nothing writes. `questions_zt.json` exists; the CSV has `keys,en,de` and lacks the options keys.

## Goals / Non-Goals

**Goals:** working language option in `account_management_screen.gd`, local-only persistence, zh_TW support, questions following language, extensible structure.
**Non-Goals:** other options, backend storage, new popup visuals.

## Decisions

1. **Reuse `Utils.set_app_locale`/`LocalCache`.** No new storage. Add `Utils.reset_app_locale()` that clears `locale` (`LocalCache.set_setting("locale", "")`) and re-runs the bootstrap resolution; refactor `_bootstrap_locale` into a `_resolve_locale()` returning the locale.
2. **Locale code `zh_TW`**, with `SUPPORTED_LOCALES = ["en","de","zh_TW"]`. OS mapping: `OS.get_locale()` starting with `zh` and containing `Hant`/`TW`/`HK`/`MO` -> `zh_TW`; otherwise language code match.
3. **Screen option registry.** In the screen script, a constant array maps dropdown item index -> locale (`LANGUAGE_LOCALES`), with `_load_options()` (sync UI from state), `_on_language_options_item_selected(index)` (apply), and `_on_revert_changes_button_pressed()` (reset all options then `_load_options()`). New options extend these three functions. Run `_load_options()` at the start of `_ready()` (before the awaited user fetch), connect signals in code or the scene.
4. **Options popup wiring.** `OptionsPopUp` uses `pop_up.gd` and its `_on_open_pop_up_button_pressed` already exists on that node; verify the scene connection works and delete the stub `_on_options_button_pressed` in the screen script.
5. **Questions.** `TriviaQuestionService._get_user_language()` reads `locale` (falling back to OS-resolved locale) and maps via `QUESTION_FILE_CODES = {"en":"en","de":"de","zh_TW":"zt"}`. Lazily-loaded per-language cache already handles switching.
6. **Translations.** Add `zh_TW` column to all CSV rows (Traditional Chinese text written for each key) plus the three missing keys in all columns; register the new `.zh_TW.translation` in `project.godot` (`locale/translations`, `locale_filter`) after the Godot editor re-imports the CSV. Assumption: translation text is authored by the implementer and can be reviewed by a native speaker later.

## Risks / Trade-offs

- The `.translation` file is generated by Godot's importer; it must be imported (open editor or `godot --headless --import`) before runtime tests.
- Chinese font coverage: the project font (Exo) may lack CJK glyphs; verify rendering and add a fallback font if needed (the dropdown already shows 繁體中文).
- Revert while locale already equals the OS locale is a no-op visually, which is expected.
